## 2. Bug resuelto: toys del personaje anterior se transferian al nuevo

**Problema:** Al usar `/cambiarpersonaje`, los accesorios visuales (toys) del personaje original —lentes, sombreros, etc.— quedaban visibles en el nuevo personaje.

**Causa:** El sistema de toys no limpiaba su estado al cambiar de personaje.

**Solucion:** Se agrego `hook OnPlayerCharSwitch` en `marp_toy.pwn` que:
- Oculta todos los objetos graficos del jugador (`Toy_HideAllGraphicObjects`)
- Descarga los datos de toys en memoria (`Toy_DisconnectionUnload`)
- Limpia el iterador de toys del jugador (`Iter_Clear`)

## 3. Bug critico resuelto: personaje volaba al cambiar

**Problema:** Al usar `/cambiarpersonaje`, el personaje nuevo salia disparado hacia arriba del mapa. Pasaba de forma intermitente, no siempre.

**Causa raiz identificada:**

El flujo original usaba `TogglePlayerSpectating(true/false)` como mecanismo de transicion:

1. `/cambiarpersonaje` → `TogglePlayerSpectating(true)` → SA-MP **guarda internamente la posicion actual** del jugador (posicion del personaje viejo)
2. Se cargan los datos del nuevo personaje, `SetSpawnInfo` se actualiza con la nueva posicion
3. `TogglePlayerSpectating(false)` → SA-MP devuelve al jugador a la **posicion guardada en el paso 1** (posicion vieja)
4. `SpawnPlayer` → teletransporta al jugador a la nueva posicion
5. El motor de fisica de SA-MP interpreta el salto de posicion como velocidad ascendente → **vuela**

El bug era intermitente porque dependia del timing entre el `TogglePlayerSpectating(false)` y el `SpawnPlayer`.

**Intentos fallidos previos (todos con la misma causa raiz):**
- `SetPlayerVelocity(0,0,0)` en el mismo tick que el spawn
- Delay de 150ms entre `TogglePlayerSpectating(false)` y `SpawnPlayer`
- `SetPlayerPos` mientras estaba en spectating para sobreescribir la posicion de retorno
- Timer de 100ms post-spawn para forzar posicion y velocidad

**Solucion final:**

Eliminar `TogglePlayerSpectating` del char switch completamente. El flujo nuevo es:

1. `/cambiarpersonaje` → se muestra `DLG_CHAR_SELECT` (mismo dialog que el login normal), el jugador sigue parado en el mundo del juego
2. Jugador selecciona personaje → `CharSwitch_DoCleanup`: guarda cuenta, limpia sistemas, destruye estructuras de items en memoria. **Sin spectating.**
3. Query a DB carga datos del nuevo personaje
4. `OnContinueCharacterLoad` → jugador **no esta en spectating** → `SpawnPlayer` directo
5. `CharSwitch_FreezeOnSpawn` congela 10 segundos por seguridad

`SpawnPlayer` directo (sin el roundtrip de spectating) no genera conflicto de posiciones → sin velocidad → sin vuelo.

**Archivos modificados:**

- `gamemodes/player/marp_cambiarpersonaje.pwn`: Se elimino `TogglePlayerSpectating(playerid, true)` y `SetPVarInt("CSwitchLoading", 1)` de `CharSwitch_DoCleanup`. Se reemplaza por `SetPVarInt("CSwitchSpawn", 1)`. Se eliminaron las funciones obsoletas `CharSwitch_DoSpawnDelayed` y `CharSwitch_FixPosVelocity`.

- `gamemodes/marp_core.pwn`: El bloque de spawn en `OnContinueCharacterLoad` paso de:
```pawn
if(GetPlayerState(playerid) == PLAYER_STATE_SPECTATING) {
    if(GetPVarInt(playerid, "CSwitchLoading")) {
        // ... SetPlayerPos + TogglePlayerSpectating(false) + SpawnPlayer
    } else {
        TogglePlayerSpectating(playerid, false);
    }
} else {
    SpawnPlayer(playerid);
}
```
A:
```pawn
if(GetPlayerState(playerid) == PLAYER_STATE_SPECTATING) {
    TogglePlayerSpectating(playerid, false);  // login normal: sin cambios
} else if(GetPVarInt(playerid, "CSwitchSpawn")) {
    DeletePVar(playerid, "CSwitchSpawn");
    SpawnPlayer(playerid);
    CharSwitch_FreezeOnSpawn(playerid);
} else {
    SpawnPlayer(playerid);
}
```

## 4. Verificacion de guardado de datos al cambiar de personaje

Se analizo si `/cambiarpersonaje` guarda correctamente los items y datos del personaje sin necesidad de usar `/q`.

**Conclusion: si, todo se guarda.** El orden en `CharSwitch_DoCleanup` es:

1. `PlayerPos_SyncCurrentData` + `SaveAccount` (con `gPlayerLogged` todavia en 1 → el `if` interno pasa)
2. `hook OnPlayerCharSwitch` → `Holster_SaveItemToDB` guarda el arma en la cadera
3. Recien despues: destruccion de estructuras en memoria

El contenido de inventarios (items en slots de container) se guarda en tiempo real en `containers_slots` con INSERT/DELETE por cada operacion. No depende del disconnect ni de SaveAccount.
